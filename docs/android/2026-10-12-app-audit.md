# Android app audit — 12–13 October 2026

Status: implementation batches are in the working tree. Findings 8, 20, and 43 received follow-up fixes on 13 October, alongside exact app-theme following and migration of the old reader palette. Verification and phone acceptance are tracked below; this is not a claim that all 47 findings have passed runtime acceptance.

This is the consolidated record of the two review passes and the follow-up on smoothness and text selection. Finding numbers 1–38 preserve the numbers used in the conversation. Findings 39 onward extend the selection review and direct phone checks. Several findings describe related symptoms; the count is not a count of independent root causes.

## Scope and evidence

Reviewed the implementation of all 15 reachable screens: Books, Poetry, Search, Audio, Kannashah, Articles, Issues, Library, Sections, Settings, Appearance, Downloads, Reader, Poem Reader, and Player. Also followed shared controls, theme preferences, navigation, playback, content loading, search, annotations, backup import/export, and the poem export pipeline.

Evidence labels:

- **Reproduced:** an isolated check exercised the existing compiled implementation or current parser. This does not mean the gesture was reproduced on the phone.
- **Code-confirmed:** a concrete behavior follows from the implementation; the corresponding phone interaction was not performed.
- **Risk:** the code contains a failure path, but the complete runtime trigger still needs verification.
- **Device-observed:** Android diagnostics recorded it on the connected phone.

The workspace already contained substantial changes before this audit. Those changes were not reverted or edited. Test/build outputs were produced; temporary probes used synthetic or existing repository test data and were removed. No personal note database was read or modified for the probes.

The user explicitly overrode the normal exclusion of GUI tests. Direct ADB gestures, screenshots, clipboard paste checks, and frame diagnostics were performed on the connected phone on 12–13 October. Runtime results below supplement the implementation review; they do not turn every code finding into a reproduced phone defect.

## Overall assessment

The app builds, but passing builds and current tests do not establish correct UI behavior. The highest priorities are annotation integrity, backup restorability, malformed poetry, the notebook duplicate-key path, theme contrast, and selection stability. The theme has a functioning central connection with important exceptions. Two real-device debug reader runs failed smoothness checks, and selection visibly jumps/reflows. Long-copy and gesture acceptance have not passed. There are 47 numbered review entries, including risks and the explicitly downgraded system-bar observation; this is not a claim of 47 reproduced bugs.

### Required runtime measurements before acceptance

Use a known APK and record device refresh rate, build type, thermal conditions, content size, and whether content is cached. Keep cold loading separate from warmed interaction. Measure a sustained, repeatable workload rather than a handful of startup frames.

| Journey | Required evidence | Current status |
|---|---|---|
| Catalog scrolling | Frame counts, frame-time/overrun percentiles, missed deadlines during sustained scrolling | Not measured adequately |
| Reader scrolling | Sustained meaningful scrolling; repeatability | Two 13-second runs on the installed short book failed; large-book/release runs pending |
| Selection handles | Continuous dragging in both directions, with exact selected range and frame timing | Extended and shortened an end handle; two app-copy payloads checked. No clean continuous timing pass |
| Edge auto-scroll | Drag past the top/bottom edge and back; anchors must stay stable | Bottom-edge attempts did not advance viewport; top-edge/reversal pending |
| Large selection | Multiple screens and beyond the current 25-block selection window | Code limitation found; gesture not measured |
| Playback plus reading | Same reading/selection workloads while audio updates | Not measured |
| Search and tab changes | Input-to-result timing and frame deadlines, not just successful navigation | Not measured adequately |

Use the device's actual frame deadline: approximately 16.67 ms at 60 Hz, 11.11 ms at 90 Hz, or 8.33 ms at 120 Hz. Averages alone cannot establish smoothness. The user's acceptance target is no visible jumps, no unexpected selection changes, and smooth dragging; a finite test cannot guarantee zero bugs under every possible condition.

## Findings 1–20: first review

### 1. Kannashah hides untagged excerpts and can generate duplicate list keys

**High; code-confirmed omission and crash risk.** Topic grouping excludes excerpts with no topics. A multi-topic excerpt is inserted into several groups using the same excerpt ID as the key in one LazyColumn. Composition of repeated occurrences can fail on duplicate keys. This crash was not reproduced on the phone.

Smallest fix: include an untagged group and use group plus excerpt identity for each occurrence. Otherwise notes can appear missing and grouped browsing can crash.

Source: [KannashahScreen.kt](../../android/app/src/main/kotlin/com/atharchive/feature/kannashah/KannashahScreen.kt), grouping around line 107 and keys around line 299.

### 2. Reader fields and footnotes mix incompatible palettes

**High; code-confirmed.** Page/volume fields use default app Material colors on the reader's independent page color. Footnote dialogs use the app container with reader-colored block text. Opposing app/reader palettes can make text hard to read.

Smallest fix: theme each complete reader component consistently, including container, text, labels, and cursor.

Sources: [ReaderPanel.kt:166](../../android/app/src/main/kotlin/com/atharchive/feature/reader/ReaderPanel.kt), [ReaderScreen.kt:230](../../android/app/src/main/kotlin/com/atharchive/feature/reader/ReaderScreen.kt).

### 3. System-bar theme connection needs cross-device verification

**Downgraded to an unconfirmed portability risk after GUI testing.** `enableEdgeToEdge()` runs once with default resource-based night detection; there is no explicit app-override/reader-palette icon update in this activity. However, on this Redmi, switching app Light/Dark changed the status-bar icons correctly. The earlier blanket claim that icons fail to follow the override was too strong. Do not count this as a reproduced theme defect.

Follow-up: test opposite app/system themes and independent reader palettes on another Android device before deciding whether explicit system-bar updates are necessary.

Source: [MainActivity.kt:33](../../android/app/src/main/kotlin/com/atharchive/MainActivity.kt). Platform behavior: [AndroidX EdgeToEdge implementation](https://android.googlesource.com/platform/frameworks/support/+/91a12edbc83943787f4e71fd3b9a74e3cbed8022/activity/activity/src/main/java/androidx/activity/EdgeToEdge.kt).

### 4. Navigation removes section state and highlights the wrong destination

**Medium; code-confirmed.** Section switching removes previous section entries before adding a new one. Local scroll/filter state does not survive like the Books root. Settings/Sections fall back to Books for bottom-bar selection even when opened elsewhere.

Smallest fix: retain tab state and derive selection from the parent destination.

Source: [AtharApp.kt:246–275](../../android/app/src/main/kotlin/com/atharchive/ui/AtharApp.kt).

### 5. Search hides filters on empty results and gives inconsistent feedback

**High; code-confirmed.** Empty results return before rendering the filter control. Counts exclude direct title matches, so zero can appear above visible matches. The text field can advance to a new query while old hits remain, without a distinct searching state.

Smallest fix: keep filters reachable, count the displayed result categories accurately, and model query freshness/loading.

Source: [SearchScreen.kt:76–100,233–255](../../android/app/src/main/kotlin/com/atharchive/feature/search/SearchScreen.kt).

### 6. Reader Contents can reopen Search; reader audio cannot pause

**Medium; code-confirmed.** The Contents action opens the panel without resetting its previous search tab. The book audio strip accepts play but no pause/current-playing state, while the global mini-player is hidden in the reader.

Smallest fix: explicitly select Contents; wire the strip to real transport state and toggle/pause.

Sources: [ReaderScreen.kt:487,809](../../android/app/src/main/kotlin/com/atharchive/feature/reader/ReaderScreen.kt), [AtharApp.kt:295,414](../../android/app/src/main/kotlin/com/atharchive/ui/AtharApp.kt).

### 7. Poem Reader settings, search destinations, and progress are incomplete

**High; code-confirmed.** Verse rendering ignores margin and tashkeel settings offered in its settings popup. Global search discards the target verse/block location. Poem progress is not saved through the reading-position mechanism. An open poem panel has no panel-first Back handler.

Smallest fix: connect the existing settings, carry the search target, persist progress, and dismiss the panel before leaving the screen.

Sources: [PoemReaderScreen.kt:96–147,318](../../android/app/src/main/kotlin/com/atharchive/feature/poemreader/PoemReaderScreen.kt), [AtharApp.kt:602](../../android/app/src/main/kotlin/com/atharchive/ui/AtharApp.kt).

### 8. Download controls conceal active and paused states

**High; code-confirmed.** Audio cards distinguish downloaded/not-downloaded but not an active request. A second tap can cancel the download while the card still presents a download action. Book-card progress uses imported blocks, and paused downloads are not represented consistently with Downloads.

Smallest fix: share queued/downloading/paused/failed/completed state across entry points.

Source: [AtharContentViewModel.kt:395–450,948](../../android/app/src/main/kotlin/com/atharchive/data/AtharContentViewModel.kt).

### 9. Success messages precede successful persistence

**High; code-confirmed.** Saving an edited note dismisses the editor and announces success before its coroutine completes. Delete/cache-clear announcements have similar timing. A later error contradicts the success message and the draft is already dismissed.

Smallest fix: await success before closing/announcing; retain a failed draft.

Sources: [AtharApp.kt:556,695–705](../../android/app/src/main/kotlin/com/atharchive/ui/AtharApp.kt), [AtharContentViewModel.kt:799](../../android/app/src/main/kotlin/com/atharchive/data/AtharContentViewModel.kt).

### 10. Playback ticks rebuild catalog-derived audio data

**Performance concern; code-confirmed work, unmeasured frame cost.** Playback publishes every 500 ms. The audio combine then walks catalog entries and rebuilds recording models, despite stable catalog data. Root UI subscribes to this state across screens.

Smallest fix: separate stable recording mapping from rapidly changing playback position. Do not claim this has been proven to cause the observed startup stalls.

Sources: [AtharContentViewModel.kt:395](../../android/app/src/main/kotlin/com/atharchive/data/AtharContentViewModel.kt), [AudioPlayback.kt:40](../../android/app/src/main/kotlin/com/atharchive/data/AudioPlayback.kt).

### 11. Long-press selection changes typography and geometry

**High for the user's selection requirement; code-confirmed.** A native TextView replaces the styled reading surface. It receives colors and font size but not the reader font, line spacing, margin, or tashkeel visibility. Padding uses raw pixels. Selection therefore does not preserve the same text geometry.

Smallest fix: preserve appearance and the visual anchor while entering selection. See findings 39–42 for deeper selection defects.

Source: [BoundedSelectionSurface.kt:32–46](../../android/app/src/main/kotlin/com/atharchive/feature/reader/BoundedSelectionSurface.kt).

### 12. Several theme colors have low contrast

**Medium; calculated from source colors.** On the light canvas, Audio/Downloads metadata at secondary alpha .72 is approximately 2.86:1; inactive bottom labels at alpha .85 are 3.62:1. Dark-reader play icons are approximately 2.47:1 against their burgundy fill. Normal text should meet the 4.5:1 contrast benchmark.

Smallest fix: use accessible text colors without excessive transparency and a dedicated foreground for filled controls.

Sources: [AudioScreen.kt:396](../../android/app/src/main/kotlin/com/atharchive/feature/audio/AudioScreen.kt), [AtharBottomBar.kt:204](../../android/app/src/main/kotlin/com/atharchive/ui/components/AtharBottomBar.kt), [ReaderScreen.kt:863](../../android/app/src/main/kotlin/com/atharchive/feature/reader/ReaderScreen.kt), [W3C contrast explanation](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).

### 13. Newest sorting is actually catalog/title order

**Medium; code-confirmed.** Articles, Issues, and Poetry preserve title-sorted database order under a Newest label. Their comparators repeatedly search the list with `indexOf`, adding unnecessary work.

Smallest fix: sort by real dates or label the existing order accurately and remove the redundant comparator.

Sources: [ArticlesScreen.kt:88](../../android/app/src/main/kotlin/com/atharchive/feature/articles/ArticlesScreen.kt), [ContentDatabase.kt:185](../../android/core/data/src/main/kotlin/com/atharchive/core/data/db/content/ContentDatabase.kt).

### 14. Arabic matching and highlighting differ across screens

**Medium; code-confirmed.** Books normalizes Arabic while several other lists use raw substring matching. Hamza/tashkeel variants can work in one list and fail in another. Raw highlighting can also fail to mark a normalized match.

Smallest fix: reuse existing normalization and source-offset mapping consistently.

Sources: [BooksScreen.kt:129](../../android/app/src/main/kotlin/com/atharchive/feature/books/BooksScreen.kt), [ArticlesScreen.kt:82](../../android/app/src/main/kotlin/com/atharchive/feature/articles/ArticlesScreen.kt), [AtharHighlight.kt](../../android/app/src/main/kotlin/com/atharchive/ui/components/AtharHighlight.kt).

**Medium; reproduced data mismatch.** Total blocks include headings/prose/page markers. In the local generated catalog, 29 of 108 poems have different total-block and verse-record counts. Jazariyyah has 210 total blocks versus 107 verse records.

### 16. Audio-card play icons never show playing state

**Medium; code-confirmed.** Cards pass `playing = false`; their action plays rather than toggles pause. The currently playing recording therefore looks stopped.

Smallest fix: bind current recording and playback state to each control.

### 17. Player display diverges from queue and sleep-timer state

**Medium; code-confirmed.** Sorting the displayed queue leaves actual playback order unchanged. Sleep minutes are remembered by the screen separately from the active timer, so leaving/reopening or timer expiry can leave a misleading label.

Smallest fix: present actual queue order and observable timer state.

### 18. Collection selection uses titles; non-audio collections appear as playlists

**Medium; code-confirmed.** Duplicate collection names resolve to the first title match. All collections appear as audio playlists, even when no audio members exist; playing such a collection silently does nothing.

Smallest fix: select by ID and represent playable/empty collections accurately.

**Performance/UX concern; code-confirmed.** Search uses non-lazy horizontal rows for all source and author options. The local full catalog has 4,240 entries, making title selection burdensome and constructing many off-screen controls. This full catalog size was not assumed to be installed on the phone.

Smallest fix: searchable lazy option lists.

## Findings 21–38: deeper review

### 21. Annotation recovery overwrites newer edits and resurrects deleted notes

**Critical; reproduced with the compiled repository and in-memory store.** Recovery snapshots annotations, suspends for content lookup, then unconditionally writes the old records. An intervening edit is replaced; an intervening deletion is undone.

Probe output: `Edited during reattachment -> new text replaced by old text`; `Deleted during reattachment -> note resurrected`.

Smallest fix: conditionally update attachment fields against the current record/version, without restoring deleted records or overwriting note text.

Source: [AnnotationRepository.kt:146–151](../../android/core/data/src/main/kotlin/com/atharchive/core/data/annotation/AnnotationRepository.kt).

### 22. The app can reject its own exported backup

**Critical; reproduced with compiled annotation/archive code.** A valid multi-block selection has start offset 10 and end offset 3 in different blocks. Approximate page recovery changes both ordinal hints to the same block but preserves offsets. Export succeeds; import rejects `invalid annotation range`. One record can prevent archive restoration.

Probe: `Approximate ordinals=80,80 offsets=10,3` followed by the import rejection.

Smallest fix: separate approximate navigation location from original endpoints and make validation consistent with the representation.

Sources: [AnnotationRepository.kt:200–205](../../android/core/data/src/main/kotlin/com/atharchive/core/data/annotation/AnnotationRepository.kt), [UserDataArchive.kt:95](../../android/core/data/src/main/kotlin/com/atharchive/core/data/archive/UserDataArchive.kt).

### 23. Incomplete or unrelated backups can be accepted as success

**High; reproduced with compiled archive code.** A two-record export truncated after its first complete record imports one record without a corruption error. There is no completion/count check. `{}` alone is accepted as an empty archive because the header fields default to valid values.

Smallest fix: explicit required format identification and a completeness check. Otherwise a partial restore can be mistaken for a full restore.

Source: [UserDataArchive.kt:45–85,128–132](../../android/core/data/src/main/kotlin/com/atharchive/core/data/archive/UserDataArchive.kt).

### 24. Poem parsing collapses many verses into one, or produces no verses

**Critical content/UI defect; reproduced on current source and generated packages.** The parser treats a Markdown paragraph as a verse and splits only its first separator. A simple two-line poem becomes one verse with the second verse embedded in its closing half.

All 108 current published poem files were parsed: 50 produce multiline hemistich fields; 8 retain unsplit `---` separators inside closing fields. Examples:

- Nuniyyat al-Qahtani: one verse record, closing field 58,735 characters.
- Lamiyyat Ibn Taymiyyah: zero verse records despite 732 characters of poem body. Android filters out the paragraph, leaving an empty poem body.
- Qasidat Ibn Abi al-Aswad: four verse records against 231 timing cues; 227 cues reference nonexistent verse numbers in the generated package.

Smallest complete fix: correct verse boundaries, validate timings against parsed verse numbers, regenerate affected packages, and provide a safe body fallback for unsupported poem structures. This affects layout, alignment, numbering, search destinations, and audio following.

Sources: [parser.ts:326–350](../../src/lib/app-v2/parser.ts), [generator.ts:167–186](../../src/lib/app-v2/generator.ts), [AtharContentViewModel.kt:1030](../../android/app/src/main/kotlin/com/atharchive/data/AtharContentViewModel.kt).

### 25. Downloads serialize unrelated reading work behind network waits

**High responsiveness risk; code-confirmed.** Text downloads, catalog sync, and uncached frame opening share a mutation mutex held across network calls. A slow download delays other operations needing that lock. Blocking HTTP calls are not connected to coroutine cancellation; a stalled read must return before between-read cancellation checks help.

Smallest fix: keep network waits outside the shared mutation lock and cancel underlying calls promptly. This does not mean every already-cached page is blocked.

Sources: [ContentTransferRunner.kt:60–92](../../android/core/data/src/main/kotlin/com/atharchive/core/data/repository/ContentTransferRunner.kt), [ReadThroughContentRepository.kt:72,108](../../android/core/data/src/main/kotlin/com/atharchive/core/data/repository/ReadThroughContentRepository.kt), [AppContentHttpClient.kt:158–160,197](../../android/core/data/src/main/kotlin/com/atharchive/core/data/network/AppContentHttpClient.kt).

### 26. Saved playback addresses become stale after download changes

**High; code-confirmed.** Queue persistence stores resolved network/file addresses. Streaming then downloading can leave a network URL queued despite an available local file. Removing a downloaded file leaves queued file URLs pointing to it. Queue restoration does not resolve current availability. Same-item/same-queue play checks compare identities, not changed URIs.

Smallest fix: resolve media IDs against current local availability during preparation/restoration and refresh stale queue entries.

Sources: [AudioPlaybackService.kt:43–58](../../android/app/src/main/kotlin/com/atharchive/data/AudioPlaybackService.kt), [AudioPlayback.kt:55](../../android/app/src/main/kotlin/com/atharchive/data/AudioPlayback.kt), [ContentDataModule.kt:187](../../android/app/src/main/kotlin/com/atharchive/data/ContentDataModule.kt).

### 27. Book/poem playback queues unrelated works

**Medium; code-confirmed.** Reader callbacks pass only the recording ID. `playAudio` defaults to the complete recording catalog, so Next/automatic advancement can leave the current work.

Smallest fix: pass the current work's ordered recordings explicitly.

Sources: [AtharContentViewModel.kt:424](../../android/app/src/main/kotlin/com/atharchive/data/AtharContentViewModel.kt), [AtharApp.kt:414,459](../../android/app/src/main/kotlin/com/atharchive/ui/AtharApp.kt).

### 28. Buffering looks stopped and the toggle cannot cancel play intent

**Medium; code-confirmed.** UI state exposes `playing` but no preparing/buffering state. During buffering, `isPlaying` is false; tapping the toggle calls prepare/play again instead of pausing the pending playback.

Smallest fix: expose buffering and play intent independently and make pause work during preparation.

Source: [AudioPlayback.kt:70–96](../../android/app/src/main/kotlin/com/atharchive/data/AudioPlayback.kt).

### 29. Player and Poem Reader have blank unavailable-state paths

**High; code-confirmed.** Routes render only inside non-null state branches. Missing/restoring state supplies no loading/error/retry/visible-back UI. Poem text loading also lacks a distinct body loading/error state when the catalog record exists but blocks are missing.

Smallest fix: explicit loading, unavailable, and retry states around both routes.

### 30. Quoted catalog queries match separated, reversed, and cross-field words

Smallest fix: proper phrase matching for the catalog index or explicit candidate verification.

### 31. Search silently stops at 12 catalog and 50 text matches

**Medium; code-confirmed.** Global search has fixed caps without pagination or a first-results notice. Author/title queries can hide additional works beyond the first 12.

Smallest fix: expose the limit and a way to retrieve the remaining results.

### 32. Restored visible query can disagree with the ViewModel query

**Medium restoration risk; code-confirmed missing connection.** The UI restores its query with `rememberSaveable`, while a new ViewModel initializes its query to empty. There is no handshake to resend restored text, allowing a populated field with default/empty results until edited.

### 33. Library never renders saved audio and hides retained unpublished works

**High; code-confirmed.** Audio saves/memberships use `audio:<id>`, but Library maps only currently published text catalog entities. Collections can count audio members with no visible Library row. Retained personal works removed from the catalog are also excluded even if their metadata is protected.

### 35. Poem audio choices hide recording titles

**Medium; code-confirmed.** Mapping sets all collection labels to `المنظومات` and reciters to empty. The chooser displays those fields instead of available track titles. Alternative recordings can be distinguishable only by duration.

## Selection follow-up: exact range and long copying

The user's requested behavior is: no jump when selection starts or scrolls; no unwanted word added; handles remain anchored to the intended text; scrolling up/down does not turn a partial selection into a whole paragraph/document selection; long passages can be copied easily across screen and loading boundaries.

The current implementation has a native selection surface with source endpoints, but this requirement is **not met or verified**. The following findings extend the original typography mismatch in finding 11.

### 39. Long press initially selects the entire block, not the touched word

**High; reproduced document logic, code-confirmed binding, and device-observed whole-line initialization.** The gesture callback passes only a Boolean used to position the toolbar, not the touched character/word. `SelectionDocument.around` chooses the whole center block's start/end and `bind` passes both to `Selection.setSelection`.

A compiled-code probe with paragraph `block 30 alpha beta gamma` produced that entire paragraph as the initial selection. A long malformed verse can make the initial selection enormous.

Smallest fix: preserve a touched word/range as semantic endpoints and initialize native selection to those endpoints, while retaining visual position.

Sources: [ReaderBlockView.kt:85–86](../../android/app/src/main/kotlin/com/atharchive/feature/reader/ReaderBlockView.kt), [BoundedSelectionSurface.kt:63–64,143–148](../../android/app/src/main/kotlin/com/atharchive/feature/reader/BoundedSelectionSurface.kt).

### 40. A changed selection document resets the user's adjusted range

**High; reproduced document changes and code-confirmed reset path.** When loaded blocks change the selection window, document equality changes. `bind` replaces the text and posts selection of the whole original center block again; it does not restore the user's current endpoints.

The compiled probe expanded a loaded window and moved the same center's initial offset from 0 to 324. The documents compare unequal. The native binding then follows its reset branch. Whether a particular handle drag triggers this on the phone remains unmeasured.

Smallest fix: preserve stable block IDs plus exact offsets across content updates; update text without reverting selection to the center block.

Source: [BoundedSelectionSurface.kt:29–30,56–65](../../android/app/src/main/kotlin/com/atharchive/feature/reader/BoundedSelectionSurface.kt).

### 41. Long selection cannot extend beyond the fixed document window

**High against the requested long-copy behavior; reproduced.** Selection is built from at most 12 blocks before the center, the center, and 12 after: 25 blocks, potentially fewer after excluding non-text blocks. The overlay has no endpoint-driven mechanism to extend that document or load the next selection range.

A probe with 60 available blocks produced a 25-block selection document. Native scrolling can only operate on text supplied to that document; it cannot select blocks absent from it. Bottom-edge gesture attempts on the phone also failed to advance the viewport; see finding 43. The 25-block cap remains a separate limitation.

Smallest complete fix: allow selection to grow while preserving stable endpoints and scroll position; do not substitute Select All for range expansion.

Source: [BoundedSelectionSurface.kt:18,127–141](../../android/app/src/main/kotlin/com/atharchive/feature/reader/BoundedSelectionSurface.kt), [ReaderScreen.kt:397–405](../../android/app/src/main/kotlin/com/atharchive/feature/reader/ReaderScreen.kt).

### 42. A missing selected block silently falls back to another block

**High correctness risk; code-confirmed conditional path.** If the selected block is absent from the supplied paging snapshot, `around` falls back to index zero and then to the first selectable segment. The next bind selects that different block rather than preserving or explicitly invalidating the intended range.

Smallest fix: retain/fetch the selected endpoints or show an explicit recoverable selection-unavailable state. Never silently select a substitute paragraph. The snapshot-loss trigger has not been reproduced on the phone.

Source: [BoundedSelectionSurface.kt:128,143](../../android/app/src/main/kotlin/com/atharchive/feature/reader/BoundedSelectionSurface.kt).

### 43. Bottom-edge selection did not scroll to additional text

**High; device-observed in the tested journey.** Starting with the author line, dragging the end handle downward selected several visible paragraphs. Moving it to y=2300 near the selection surface bottom (y=2304), then holding near the edge for three seconds using DOWN/MOVE/UP input, left the viewport unchanged. Additional text remained below the viewport. This prevented easy continuation of the long selection in these attempts; it is not a claim that every possible native edge gesture fails.

Evidence: [selection at the edge](audit-evidence/2026-10-12/reader-selection-edge.png). The fixed document cap in finding 41 and this observed within-window behavior both need acceptance tests. Use a continuous real-finger top/bottom edge test after repair, preserving the original anchor and exact endpoints.

### 44. Selection exposes two toolbars and initially hides its handles

**Medium; device-observed.** Initial long press displayed the app Copy/Share/Highlight toolbar without visible native handles. A second long press displayed native handles and Android's Select all/Copy toolbar while the app toolbar remained. The menus occupy different positions and the native handles use a cyan system color against the burgundy selection highlight.

Evidence: [both toolbars](audit-evidence/2026-10-12/reader-two-selection-toolbars.png). Unify selection entry, handle visibility, and actions so one long press produces an understandable state. Native system colors are not intrinsically a bug; the duplicated controls and inconsistent entry behavior are the usability problem.

### 45. Catalog rows expose topic identifiers instead of readable Arabic labels

**Medium; device-observed and code-confirmed.** Books shows `al-aqeedah-al-aamah`; Issues shows `aam-other`. These are internal-looking identifiers in an otherwise Arabic interface. The view model passes `topicsCsv` values directly into row models and filters.

Evidence: [Books](audit-evidence/2026-10-12/books.png), [Issues](audit-evidence/2026-10-12/issues.png). Source: [AtharContentViewModel.kt](../../android/app/src/main/kotlin/com/atharchive/data/AtharContentViewModel.kt), mappings around lines 515, 537, and 966.

Fix direction: resolve topic IDs to display names consistently in rows, filters, and search while retaining IDs for identity.

### 46. Top and bottom buttons are visually too small

**High-priority usability request from the user; supported by device inspection.** The user explicitly reports that the top and bottom buttons are very small and need fixing. Reader icons are only 19 dp; top control containers are 42 dp. The bottom reader controls provide a minimum 52 dp height but still render 19 dp symbols. Expanding a hidden hit area alone does not address tiny-looking controls, recognition, or confidence when tapping.

Fix direction: enlarge the visible icons and establish comfortable, consistent top/bottom controls across app screens, readers, player, and selection toolbars. Use at least 48 dp tappable regions as the audit acceptance target, with clear separation and Arabic action labels. Check one-handed use and large text without crowding the content.

Distinguish visual size from actual hit area: Compose may expand touch bounds, and bottom navigation items are already wider than their icons. This report does not assert that every button has an undersized hit target. Validate effective targets and overlap on the phone after changing the shared controls.

Sources: [ReaderScreen.kt:584](../../android/app/src/main/kotlin/com/atharchive/feature/reader/ReaderScreen.kt), [bottom controls:661](../../android/app/src/main/kotlin/com/atharchive/feature/reader/ReaderScreen.kt), [reader screenshot](audit-evidence/2026-10-12/reader-before-selection.png).

### 47. Player seek track retains a different Material palette

**Medium theme inconsistency; device-observed with incomplete token mapping in code.** The Player's inactive seek track is purple, contrasting with the app's warm neutral/burgundy controls. `PlayerSeekBar` uses a default Material Slider. The root color schemes override primary and some surface colors but leave other Material roles at defaults.

Evidence: [Player](audit-evidence/2026-10-12/player.png). Sources: [PlayerScreen.kt:395](../../android/app/src/main/kotlin/com/atharchive/feature/audio/PlayerScreen.kt), [AtharTheme.kt:239](../../android/app/src/main/kotlin/com/atharchive/ui/theme/AtharTheme.kt). ## First fix batch — findings 21–23
